feat(pi-tiered-subagents): tie every launch to the session that asked

A launch used to be accepted by whichever manager happened to hold it. Now
every request carries a SessionOwner token, and the manager accepts it only
while that token names the live session.

The generation is the identity; the session id is only the name Pi shows the
operator. A session that restarts with the same id still gets a fresh
generation, so a token prepared before a restart can never be accepted after
it. That is what makes "refuse a stale launch" decidable at all.

Refusal is a value, not an exception. LaunchOutcome separates "accepted" from
"rejected", and LaunchRejection names why. A launch for an ended session is
an expected answer, and both doors get to word their own message for it.

The switch handshake is three calls, because "switching" is not one moment.
beginOwnerEnd stops accepting new launches but leaves running children alone
-- Pi may still abandon the switch. beginOwner on the same id restores the
session and leaves those children running. beginOwner on a different id is the
switch taking effect, and only then are the previous session's children
cancelled. endOwner is shutdown: refuse, then cancel.

Resume is refused with stale-session for a child a later session did not ask
for, even when the id is known and the child is otherwise resumable; its
outcome went to the parent that started it.

The 14 tests here were checked against deliberate mutations: reusing a
generation fails 4, and cancelling eagerly in session_before_switch -- the
error story 84 warns about -- fails 2.
