01 FROM REQUEST TO RESULT

How a specialist becomes active.

The parent explicitly selects a role and supplies the task. The extension resolves the launch, owns the child, and delivers its outcome. Mentioning “debug” or “review” in a user message does not activate a role: there is no keyword-triggered agent picker, autonomous role activation, or automatic debug-to-worker pipeline.

Read the specs in order. SPEC.md defines the product. ARCHITECTURE-SPEC.md supersedes conflicting trust, concurrency, and programmatic-launch requirements. Historical ADR wording is not a newer authority.

01 / Invoke

The parent makes delegation explicit.

The model-facing subagent tool takes a subagent_type and a task prompt. A programmatic caller uses launch(type, prompt) for background handoff or run(type, prompt) to await a settled record.

  • All five shipped definitions default to background execution.
  • The tool can request foreground with run_in_background: false.
  • A resume ID takes the continuation path before new-launch preparation.

PARENT RESPONSIBILITY

Choose a suitable specialist and provide a bounded task. A reviewer needs requirements, scope, and a diff or readable artifact. Debug returns evidence and a repair recommendation; it does not automatically activate Worker.

Tool entryService entryShipped instructions

02 / Snapshot

Capture the request, not the future parent.

The shared Subagents seam captures session ownership, working directory, prompt/conversation inputs, and active/registered tool names before asynchronous definition loading. Preparation also copies model, routing, and launch-shaping settings inputs.

  • Later parent model or tool changes cannot widen an accepted launch.
  • Fresh conversation is the default; Debug inherits it unless explicitly overridden.
  • Standing instructions are separate from conversation history.

CAPTURED ≠ FROZEN WORLD

The loaded configuration is owned by the request, but reading multiple files is not an atomic filesystem transaction. Tool names do not freeze third-party implementation code. Concurrency, retention, and interrupt policy remain live controls.

Capture seamPreparation captureCapture tests

03 / Prepare

One authority resolves the launch.

LaunchPreparer loads a per-request catalog: shipped → global → project. It selects the normalized identifier, then resolves model, reasoning, role defaults, and turn policy. The shared seam resolves exact capability names and supported MCP patterns.

  • Request choices win over definition defaults.
  • Absent fields inherit; explicit values replace; supported null clears; an empty list stays empty.
  • Unknown, disabled, malformed, or duplicate requested definitions reject rather than become another role.

NO CHILD ALLOCATED YET

A preparation rejection creates no accepted child record or SDK session. Scope enumeration failure is not treated as an empty override layer. The extension reads project layers normally; it adds no project-trust gate of its own.

Preparation authorityConfiguration resolverRefusal tests

04 / Commit

Acceptance transfers ownership.

After preparation, the caller's cancellation and the parent-session generation are checked at the acceptance boundary. The manager registers the captured launch without an intervening asynchronous gap and returns a stable child ID.

  • launch() acceptance does not wait for capacity, SDK construction, or completion.
  • Its preparation signal detaches after acceptance; use abort(id) to stop accepted work.
  • run() retains cancellation ownership of its queued or running child.

THE IMPORTANT DISTINCTION

“Accepted” means that the runtime owns an identified child. It is not a promise that a model call has begun or will succeed. A later SDK construction/provider failure becomes that child's execution outcome, not a retroactive launch rejection.

Acceptance adaptersOwnership contractCommit-race tests

05 / Admit

Wait for capacity. Then build the real child.

Every initial and resumed run enters the same concurrency limiter. A potentially file-changing child also acquires the originating workspace's exclusive writer slot. The SDK adapter materializes the selected identity and installs the prepared capability allowlist.

  • Known readers may overlap writers, subject to available concurrency.
  • Shells, editors, and unknown capability names count as writers.
  • Management tools stay excluded across registry rebuilds; recursive delegation is not supported.

NO SILENT REROUTE

If the captured model can no longer be materialized, execution fails instead of picking another identity. The writer slot coordinates this runtime's children—not the parent, other processes, or a reader's view of files mid-write.

Admission managerSDK child assemblyReal capability tests

06 / Observe

Return an outcome. Keep control of the session.

Background completion uses the established notification/result-delivery machinery. Foreground execution claims its outcome before it can settle. Records report resolved model/reasoning facts, result or error, usage, and artifact pointers by value.

  • get_subagent_result polls or waits; stopping the wait does not stop the child.
  • steer_subagent supplies mid-run guidance. A retained eligible child can resume with a new prompt, captured configuration, and fresh turn counter.
  • Confirmed parent replacement suppresses stale delivery and cleans up owned children. A vetoed switch preserves them.

QUESTIONS ARE A HANDOFF

The child can use ask_parent to end its turn with a question; the parent can answer through resume. Background notify_parent updates are available when enabled. These protocol channels are separate from capability tools.

A practical handoff / tool-call notation

Ask Explore for a bounded answer.

For an illustrative repository with src/auth/, the parent makes this call. The prompt supplies the context because Explore starts with a fresh conversation by default.

subagent({
  subagent_type: "explore",
  description: "Trace token validation",
  prompt: "Trace token validation in src/auth/. Report entry points, checks, and absolute file paths. Do not edit.",
  run_in_background: true
})

After preparation, the tool returns an agent ID and acceptance/queue information—not the final answer. The parent can do different work while the child waits for capacity or runs. Do not duplicate its task. Without a model override in the request or definition, the child uses the family ladder.

get_subagent_result({
  agent_id: "<returned-id>",
  wait: true,
  timeout: 60
})

Omit wait to poll. The timeout is in seconds and only bounds this wait; it does not abort the child. Background completion is announced through the delivery machinery unless another caller is already collecting that outcome. Read the result/error and status, then summarize the findings for the user.

Continue deliberately / same child

Resume is not a new specialist.

If the child uses ask_parent, it records a question and ends its turn. Once settled, answer it with the same ID; a follow-up question can use the same continuation path.

subagent({
  subagent_type: "explore",
  description: "Clarify validation scope",
  resume: "<returned-id>",
  prompt: "Include the refresh-token path too; exclude test fixtures.",
  run_in_background: true
})

Resume continues the retained session with its captured configuration; it does not reselect a model or reload a new role. Omit run_in_background: true on a resume to await its outcome inline. A running child needs steer_subagent, not resume. Released, stale, or otherwise ineligible sessions refuse resume; results remain available within the owning parent session.

The parent owns the next decision. To turn findings into a change, explicitly invoke worker with the evidence and a scoped task; to review it, explicitly invoke reviewer with requirements and a diff or readable artifact. Debug similarly returns a diagnosis, not an automatic Worker launch.

Children cannot delegate recursively: subagent, get_subagent_result, and steer_subagent are stripped from their capabilities. ask_parent and enabled notify_parent are communication channels, not permission to start more agents.

Tool calls and service calls are two doors, not two workflows. The examples above describe model-facing tools, not JavaScript functions exported by the package. Another extension obtains getSubagentsService() and calls launch("explore", prompt) for { kind: "accepted", id }, or run("explore", prompt) for { kind: "settled", record }. Either can return { kind: "rejected", reason, message } before any child exists; “settled” can mean completed, stopped, or error.

Both use the same preparation, model policy, capability enforcement, and scheduling. Service callers inspect getRecord(id), use steer(id, message) or abort(id), and call resume(id, prompt) to continue. Service resume schedules background work but its promise resolves at settlement; it is not an immediate ID-returning launch. Service options use thinkingLevel, maxTurns, and inheritContext, rather than the tool's snake_case fields. Exact public contract →

03 MODEL FIRST, REASONING SECOND

A declared ladder. Not a price guess.

“Tiered” means explicit relationships within a model family. It does not mean ranking every available model by cost, guessing equivalent versions, or always using the cheapest candidate.

Model selection

Specific choices beat automatic policy.

  1. Exact model in the request
  2. Exact model in the effective definition
  3. Automatic family-ladder routing

Use model: "anthropic/claude-sonnet-5" in a tool call or service options, or model: anthropic/claude-sonnet-5 in an agent file's frontmatter. The request wins over the effective definition. Both bypass automatic routing, even for a family the router cannot recognize.

An explicit identity must be provider/modelId, never a fuzzy name such as sonnet. Provider matching is case-insensitive; the model ID is exact and may itself contain slashes. An unavailable identity fails instead of silently choosing a different provider or model.

Parent→Lower / unavailable→Next / available

Automatic routing tries compatible lower tiers in the same version first, in declared model preference order. Crossing versions requires explicit profile links. It never synthesizes target IDs.

PrecedenceLadder walkRouting tests

Reasoning selection

Use what the resolved model supports.

  1. Thinking level in the request
  2. Thinking level in the effective definition
  3. One rung below the parent's effort, in the child's own level array

Pi reports each model's levels as an array, and the arrays have gaps: ["low","high","max"] for 55 catalogue models, ["medium","xhigh"] for one, ["off","high"] for 58. A step down is therefore the highest supported level strictly below the parent's — max → high → low — never arithmetic on a fixed index.

At the model's floor the effort stands and the launch note says so; on a model whose floor is above the parent's effort (only high, for example) it says the model has no lower rung. With no parent effort to step down from — a standalone or programmatic launch — the order is medium → low → lowest supported non-off. Explicit requests still win, unsupported levels are clamped, and a non-reasoning model reports not applicable.

How the walk actually works

Same version first. Only declared crossings.

  1. Locate the parent by family, version, and most specific matching tier. For example, flash-lite is not the flash rung. Recognized date/serving qualifiers can still identify a tier.
  2. Try every tier below it in that version, in order; within each rung, try the listed provider/ID pairs in preference order. Skip unavailable candidates.
  3. If none works, follow only that starting rung's declared fallback links. At a fallback target, try the target itself, then its lower same-version rungs, then its own fallback links. Do not borrow links from skipped lower rungs.

For example, gpt-6.1-sol can reach gpt-6-luna, then gpt-5.6-luna if needed. It does not try 6 astra or sol. A 3.7 Qwen max parent prefers 3.7 plus; if unavailable, it tries 3.6 plus then 3.6 flash. A 3.7 plus parent cannot make that crossing.

Availability & operator overrides

The session decides what can run.

Automatic routing only selects concrete provider/ID pairs listed in the profile and reported runnable by the session. It does not invent credentials or transfer an ID to OpenRouter, a bridge, or another provider. A recognized parent alias may locate a rung without becoming an eligible target: target IDs must still be listed.

Agent definitions layer shipped → global → project. To fix Explore's model, put model: anthropic/claude-sonnet-5 in .pi/agents/explore.md; omit the field to inherit the lower definition, or set model: null to clear an inherited fixed model and return to automatic selection when the request names none.

To change automatic policy, set familyProfiles in the shared extension-settings store. Global then project overrides replace each named family whole—versions, tiers, candidates, and fallback links are not merged. Other families stay unchanged. Profiles are validated data, not executable matchers; a new naming family needs code support, not just JSON. Configuration examples → · Validation and replacement →

Error, retention, and failure are different. An unknown family rejects automatic routing and asks for an explicit model. A recognized family with no profile, no matching version/tier, or no available lower target keeps the parent model and applies the reasoning fallback; for example, an unprofiled GPT version is not guessed into the nearest numbered ladder. With no parent model, there is no step-down decision.

An explicit override that cannot resolve is an error, never an invitation to walk the ladder. Even a successfully selected identity can fail later during execution if it can no longer be materialized or the provider fails; the runtime reports that failure rather than silently rerouting. Inspect the launch note for the chosen identity and reason.

06 WHY THIS SHAPE — AND WHAT IT COSTS

Useful guardrails. Real trade-offs.

The benefits follow from explicit policy, not from promising that delegation is always cheaper, faster, or safer than doing the task in the parent.

What you gain

Less repeated decision-making.

  • Inspectable model choices

    Profiles replace fuzzy names and price heuristics. Actual identity, thinking applicability, and selection reason remain visible.

  • Focused capability defaults

    Read-only roles do not need a shell. Worker and Debug follow the session's chosen active tools rather than a second hardcoded environment.

  • Predictable queued work

    Accepted definitions, context policy, tools, and turn budgets do not drift with later parent edits. Both launch doors share preparation.

  • Controlled overlapping work

    Readers can overlap; potential writers serialize. Distinct cancellation and session ownership reduce accidental termination and stale delivery.

What you pay / retain responsibility for

Policy is not a universal optimizer.

  • Ladders need maintenance

    New releases or naming structures can require data or code changes. Unknown families need an explicit model; a retained parent may save no model cost.

  • Delegation has overhead

    Preparation, child context, model calls, and coordination add latency and tokens. A lower tier may be a poor fit for a difficult task.

  • Conservative serialization can bottleneck

    Unknown tools count as writers, even if they are actually read-only. Foreground work can queue. A reader can still see files during another child's write.

  • Trust and tool code still matter

    Allowlisted tool names are not OS isolation. Third-party tools/extensions remain executable code; Debug's role instructions do not remove its editing capabilities.

07 THE HONEST COMPLETENESS ANSWER

Substantially complete.
Not an unlimited guarantee.

The approved core is implemented.

The inspected source and focused tests support that conclusion, and the repository records stabilization as complete. Calling this “just a port” or “unfinished tier scaffolding” would now be misleading.

Calling it universally production-proven would also be misleading. This guide is a grouped source audit, not a fresh story-by-story certification, vendor benchmark, security audit, or release approval.

Read the evidence and standing constraints →

Release readiness is a separate human decision

The documented stabilization queue is closed, with packed installation, public types, runtime floor, SDK, and MCP evidence. That is not authorization to publish, nor proof that every deployment environment is covered. This site neither publishes nor exercises a live agent.

No live vendor-response validation

SDK checks substitute external model responses while running real loading, binding, dispatch, tool pipelines, and lifecycle behavior. They establish compatibility at those boundaries—not vendor uptime, quality, current availability, or cost savings. Shipped profiles are representative catalog data.

No sandbox, recursive tree, or automatic repair pipeline

The writer slot does not coordinate parent/user edits or other processes. It does not give readers a consistent snapshot. Management tools are excluded from children, so nested delegation is out of scope. Debug diagnoses; the parent decides whether to ask Worker to implement a repair.

Project configuration has no second trust gate

The architecture deliberately removed extension-owned trust gating. Global and project definitions/settings are read while the extension runs. Pi owns its own loading/resource policy, but this does not prove that Pi separately approves each directly read project file.

Cleanup is bounded; discovery is single-owner

A factory or workspace provider that never returns cannot have its not-yet-produced resource disposed. Late arrivals are cleaned up when they arrive; parent shutdown does not hang indefinitely. Service publication is guarded against child/stale owners, but remains one service per package identity—not a concurrent multi-parent registry.

Configuration and presentation caveats remain

The old subagents.json file is not migrated automatically. The shared /extension-settings menu needs its extension loaded first; storage works independently. Third-party type diagnostics are pinned and checked, not absent. The status record also notes that longer key hints may be dropped in an 80-column transcript footer.
